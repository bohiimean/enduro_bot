# Telegram-бот — техническое задание

Статус: архитектура и стек зафиксированы, разработка не начата.
Этот документ — источник истины по принятым решениям. Не пересматривать архитектуру без явного запроса.

## Контекст

Низкая нагрузка — ориентир ~10 пользователей в час. Все архитектурные решения исходят из этого масштаба. БД, Redis, Celery, Django сознательно не используются — они избыточны при такой нагрузке и добавляют сложность без выгоды. Если нагрузка вырастет до 400-500+ чел/час — см. раздел "Порог пересмотра архитектуры" в конце файла.

Telegram заблокирован в РФ — бот обязан работать на зарубежном VPS, российский хостинг не вариант (сервер физически не достучится до api.telegram.org).

## Функционал

### 1. Курс валют

Пользователь нажимает кнопку — бот присылает одно сообщение с курсом и итоговой ценой по каждому способу оплаты (курс + наценка).

**USDT/RUB** — решено:
- Источник: Rapira API, публичный эндпоинт, без авторизации
  ```
  GET https://api.rapira.net/open/market/rates
  ```
  Лимит: 5 запросов/сек, не более 100/мин — для нашей нагрузки избыточный запас.
  В ответе ищем пару `USDT/RUB`, берём `close` (или среднее `bidPrice`/`askPrice`).
- Итоговая цена = курс × 1.045 (комиссия/наценка +4.5%, фиксированная).
- Доступные на Rapira пары (для справки, остальные сейчас не используются): `USDT/RUB`, `BTC/USDT`, `TRX/USDT`, `ETH/USDT`, `ETH/BTC`, `USDC/USDT`, `BNB/USDT`. Пары USD/RUB на Rapira нет — это крипто-биржа.

**USD/RUB** — НЕ РЕШЕНО, отложено клиентом. Пока заглушка (см. раздел "Реализация курса" — `UsdRubStubProvider`). Рассмотренные и отклонённые/возможные варианты — см. "Открытые вопросы".

**Кеширование курса**: in-memory, TTL 3-5 минут (точное значение — конфигурируемо). Не дёргать внешний API на каждое сообщение пользователя.

### 2. Статус заказа

Пользователь вводит номер телефона — бот возвращает статус заказа(ов). Клиент подтвердил: поиск по номеру телефона (`ФИО` в таблице — для отображения/проверки совпадения, не ключ поиска). В реальной таблице нет отдельного номера заказа, поэтому это единственный рабочий вариант, не опция на выбор.

Источник данных — Google Таблица, лист `Orders`. **Прямых обращений к Google Sheets на каждый запрос пользователя нет** — данные читаются в память при старте и обновляются по таймеру (см. "Реализация Google Sheets").

Клиент продолжает вести таблицу как обычно — никакой админки, никакой миграции в БД на этом этапе.

### 3. Каталог товаров (наличие)

Категории (по бренду, колонка `Марка`) → список моделей с пагинацией → карточка (модель, цвет, цена, наличие, кнопка «Связаться с менеджером»).

Покупки через бота не делаем — только просмотр и контакт с менеджером (решено).

Источник данных — тот же лист `Orders`, не отдельный лист. Каталог — это строки Orders, где колонка `Статус` = "в наличии" (см. "Реализация Google Sheets").

Навигация по каталогу — через `callback_data` кнопок (весь контекст: категория, страница, id товара кодируется прямо в кнопке), без хранения состояния пользователя на сервере:
```
cat:{category}:page:{n}
item:{product_id}
```

## Технический стек

| Компонент | Технология | Комментарий |
|---|---|---|
| Бот | aiogram 3.x (Python, async) | long polling, не webhook |
| Данные (заказы, товары) | Google Sheets API | сервисный аккаунт, read-only |
| Кеш курса и листов | in-memory (Python dict + TTL) | без Redis |
| Фоновые задачи | APScheduler | без Celery |
| БД | нет | при текущей нагрузке не нужна |
| Контейнеризация | Docker + docker-compose | один контейнер, без оркестрации (k8s избыточен) |
| Хостинг | зарубежный VPS | обязательно — Telegram заблокирован в РФ |

**Почему long polling, а не webhook**: webhook требует HTTPS-эндпоинт, сертификат, nginx. При такой нагрузке это чистые накладные расходы без выгоды. Polling — один Python-процесс, без веб-сервера.

**Почему без БД**: единственный аргумент за БД на этом масштабе — защита от случайной потери данных в таблице (если клиент удалит строку). Это не техническая необходимость, а вопрос договорённости с клиентом. Сейчас не реализуем.

## Реализация курса валют

Интерфейс провайдера курса — чтобы безболезненно подключить реальный источник USD/RUB, когда он определится:

```python
class RateProvider:
    async def get_rate(self) -> Decimal: ...

class RapiraProvider(RateProvider):
    MARKUP = Decimal("1.045")  # +4.5%, решено и зафиксировано

    async def get_rate(self) -> Decimal:
        data = await fetch("https://api.rapira.net/open/market/rates")
        usdt_rub = next(p for p in data["data"] if p["symbol"] == "USDT/RUB")
        return Decimal(str(usdt_rub["close"])) * self.MARKUP

class UsdRubStubProvider(RateProvider):
    """Источник USD/RUB не определён. Заглушка — заменить, когда решится."""
    async def get_rate(self) -> Decimal:
        return Decimal("0")
```

Курс достаётся через кеш с TTL и `asyncio.Lock`, чтобы при параллельных запросах не было повторных обращений к API:

```python
class RateCache:
    def __init__(self, ttl_seconds: int):
        self._ttl = ttl_seconds
        self._store: dict[str, tuple[Decimal, float]] = {}
        self._lock = asyncio.Lock()

    async def get_or_refresh(self, key: str, provider: RateProvider) -> Decimal:
        async with self._lock:
            cached = self._store.get(key)
            if cached and time.time() - cached[1] < self._ttl:
                return cached[0]
            rate = await provider.get_rate()
            self._store[key] = (rate, time.time())
            return rate
```

**Фолбэк при сбое Rapira API**: вернуть последнее закешированное значение с пометкой времени ("курс на HH:MM"), не ронять хендлер. Залогировать ошибку.

## Реализация Google Sheets

Схема подтверждена реальным фрагментом таблицы (`фрагмент.xlsx`) — клиент сообщил, что структура 1:1 совпадает с Google-таблицей.

**Orders** (в рабочей таблице — `Лист1`) используется для статуса заказа.

**Каталог живёт на отдельном листе (`Лист2`), а не в Orders — так сделано в итоге.** Изначальный план (каталог = строки Orders со `Статус` = "в наличии") отменён: у листа каталога свои колонки — `название` / `описание` / `цена` / `фото` (ссылка на Google Drive), заголовки приводятся к нижнему регистру. Читает его `CatalogCache`, отдельно от `SheetsCache`. Побочный плюс: вопрос утечки персональных данных в каталог снят по построению — `ФИО`/`Телефон`/`Город`/`ТК` на этом листе просто отсутствуют, и явный allowlist полей (`to_catalog_card`) больше не нужен. Оба кеша наследуют `services/sheet_reader.py`, который и делает всю общую работу.

| дата | Цена | Оплачено | Остаток | Марка | Модель | Прог-я | Цвет | кол-во | Статус поставки | Статус | ФИО | Телефон | Город | ТК |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

`Статус` — новая колонка (добавляется клиентом), значения `"в наличии"` / `"нет в наличии"`. Не путать с `Статус поставки` (свободный текст про ETA доставки) — это две разные колонки, существуют одновременно.

Важные особенности реальных данных, влияющие на реализацию:

- **Номера заказа как отдельной колонки нет.** Уникального ID в таблице не существует. Поиск возможен только по `Телефон` — клиент подтвердил это явно.
- **Один телефон — возможно несколько строк.** Один клиент может иметь несколько заказов (разные модели/даты). Бот обязан возвращать все совпадения, а не первое найденное.
- **"Статус поставки" — свободный текст, не enum.** Реальные значения: `"в пути - начало июля в Москве"`, `"после 20 июня в Москве"`, `"свяжитесь со мной по этой модели в понедельник"`. Оператор вписывает текст руками, фиксированного списка статусов нет. Бот отдаёт это значение как есть — никакой нормализации или маппинга на enum.
- **`Прог-я` (link / no link)** — назначение не до конца понятно (возможно, отметка о наличии трек-номера у партии). **Уточнить у клиента**, нужно ли показывать это поле пользователю или оно служебное, для внутреннего использования.
- `дата` хранится как число (серийная дата Excel/Sheets) — при выводе клиенту форматировать в `ДД.MM.ГГГГ`.

Доступ к таблице — через сервисный аккаунт Google Cloud (Sheets API включить в проекте, JSON-ключ на сервере, таблица расшарена на email сервисного аккаунта с правом просмотра — запись не нужна, бот только читает).

Кеш листа в памяти, обновление по таймеру через APScheduler (не на каждый запрос пользователя):

Общая механика — в `services/sheet_reader.py`: лист читается целиком, первая строка становится заголовками, короткие строки добиваются пустыми значениями. Наследники переопределяют только разбор: `SheetsCache` приводит серийную дату к `ДД.ММ.ГГГГ`, `CatalogCache` опускает заголовки в нижний регистр.

```python
class SheetsCache(SheetReader):
    def _parse_row(self, record: dict) -> dict:
        if "дата" in record:
            record["дата"] = _parse_date(record["дата"])
        return record

    def find_orders_by_phone(self, phone: str) -> list[dict]:
        target = normalize_phone(phone)
        return [o for o in self._rows if normalize_phone(o.get("Телефон", "")) == target]
```

`normalize_phone()` — обязательно нормализовать номер перед сравнением (убрать пробелы, скобки, дефисы, привести `8`/`+7` к одному виду), иначе совпадения будут теряться из-за разного формата ввода у клиентов.

Интервал обновления — 5-10 минут (конфигурируемо, см. `.env`).

**Фолбэк при сбое обновления**: если плановый рефреш не удался — оставить предыдущие данные в кеше, не перезатирать пустым результатом. Залогировать ошибку.

## Деплой

- Зарубежный VPS (Hetzner, DigitalOcean и т.п.) — обязательное условие, не опция.
- **Запуск через Docker** (решено добавить контейнеризацию — без неё дальше не двигаемся).

```dockerfile
# Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

```yaml
# docker-compose.yml
services:
  bot:
    build: .
    restart: unless-stopped
    env_file: .env
    volumes:
      - ./credentials.json:/app/credentials.json:ro
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

- JSON-ключ сервисного аккаунта Google монтируется volume'ом, не запекается в образ.
- Логи — стандартный `logging` в stdout, Docker сам пишет их через `json-file` driver (лимиты выше не дают логам разрастаться бесконечно — отдельный logrotate не нужен).
- Перезапуск при падении — `restart: unless-stopped`. Отдельный systemd-юнит не нужен; если на сервере уже настроен автозапуск Docker при перезагрузке — `docker compose up -d` достаточно.
- Webhook/nginx/SSL всё ещё не нужны — long polling работает из контейнера так же, как из обычного процесса.

## Приём оплаты через Alfabit (QR + KYC) — в разработке

Цель: принимать **рубли по СБП с верификацией плательщика (KYC)** за продажу юаня. Реализуется в ветке `feat/alfabit-qr-kyc`. Сервис — [alfabit.org integration API](https://alfabit.org/ru/api-docs).

**Что делает метод.** Alfabit выступает эквайером: генерирует QR/реквизиты СБП, принимает рубли на баланс аккаунта, KYC сверяет ФИО плательщика. Выдачу юаня бот по-прежнему делает сам после подтверждения оплаты — метод закрывает только приём рублей.

**Авторизация.** Все запросы подписываются HMAC-SHA256. Заголовки `X-API-Key` / `X-API-Signature` / `X-API-Timestamp`, где `message = "{timestamp}{METHOD}{path}{body}"`, timestamp живёт 5 минут. Ключи `pk_live_*` / `sk_live_*` из кабинета alfabit.

**Ключевые эндпоинты:**
- `GET /api/v1/integration/converter/fiat/rate?crypto=USDT&fiat=RUB&direction=buy` — курс USDT/RUB «обменник» (со спредом alfabit). Используется для строки курса QR+KYC.
- `POST /api/v1/integration/checkout/payments` — создать RUB-платёж. Если плательщик не верифицирован → `status=kyc_required`.
- `POST /api/v1/integration/checkout/payers/{phone}/documents` — загрузка фото паспорта (multipart), KYC. Ключ верификации — телефон, проверяется один раз.
- `GET /api/v1/integration/checkout/payers/{phone}` — статус KYC (`not_started|pending|approved|rejected`), отдаёт `expected_payer_name`.
- `GET /api/v1/integration/checkout/payments/{uid}` — статус платежа + `qr_url`/`qr_payload`.

**Решения:**
- **Поллинг вместо webhook** — webhook требует публичный HTTPS-эндпоинт (противоречит «no nginx»). Пользователь жмёт «✅ Я оплатил» → бот дёргает `GET .../payments/{uid}`.
- **БД не нужна** — `payment_uid` кодируется прямо в `callback_data` кнопки (как в каталоге), состояние на сервере не хранится. Опционально: аудит-лог оплат в отдельный лист Google Sheets.
- Курс alfabit включается **только при наличии ключей** — без них бот работает как раньше.

**Сделано:** `services/alfabit/client.py` (подписанный клиент), `services/rate_providers/alfabit.py` (`AlfabitWidgetProvider` — курс витрины кабинета, подключён в main; `AlfabitProvider` — базовый курс конвертера, остался запасным путём), переменные `ALFABIT_*` в config, строка «QR + KYC» в `handlers/rates.py`, `services/public_ip.py` (payer_ip), `handlers/payment.py` (платёжный FSM), `services/kyc_watch.py` (фоновое слежение за заявкой), `services/kyc_trace.py` (след KYC в логах), `handlers/errors.py` (глобальный error-хендлер).

**Порядок шагов в `handlers/payment.py` намеренно отличается от схемы в доках alfabit.** В доках: платёж создаётся первым и возвращает `kyc_required`. У нас: телефон → KYC → и только потом количество юаней, свежий курс, создание платежа, QR. Причина: пользователь вводит **количество юаней**, значит рублёвая сумма — это обязательство, зафиксированное по курсу на момент создания платежа. Если считать курс до KYC, окно фиксации растянулось бы на всю верификацию (а она может уйти на ручную сверку — это не секунды). При текущем порядке курс зафиксирован от QR до оплаты.

Формула суммы: `количество юаней × yuan_price(курс alfabit)`, где `yuan_price` — общий с строкой курса (`services/yuan.py`, делитель 6.63). Считаем по **отображённой** (округлённой до копейки) цене юаня, иначе итог разойдётся с тем, что человек видит в сообщении курса.

Уведомление менеджеру об оплате требует `MANAGER_TG_CHAT_ID` — по юзернейму Telegram писать не даёт, и менеджер должен один раз нажать `/start` у бота. Без переменной уведомление уходит только в лог, флоу не ломается.

**Отрезок «телефон → пройденный KYC» защищён отдельно (08.08.2026).** Разбор реального случая: пользователь загрузил главную страницу паспорта, дважды нажал «🔎 Статус верификации», затем прислал прописку — и она не ушла никуда. Причина: `kyc_status` регистрируется раньше FSM-хендлеров и безусловно делал `set_state(None)`, а в aiogram 3 хендлер без `StateFilter` срабатывает в любом состоянии. Шаг уничтожался, следующее фото не подходило ни одному хендлеру, catch-all отсутствовал — бот молчал. В Alfabit остался один документ из двух, плательщик навсегда завис в `kyc_status: pending`.

Что сделано, чтобы этот класс ошибок не повторялся:
- `kyc_status` и любые кнопки меню **не трогают шаг сценария**: если состояние не `None`, бот отвечает подсказкой, чего ждёт, и возвращает клавиатуру текущего шага.
- Оба шага загрузки — один хендлер `handle_document` под `asyncio.Lock` на пользователя; слот определяется **внутри замка** по актуальному состоянию. Без этого два быстрых сообщения подряд (Telegram шлёт их отдельными update'ами, aiogram обрабатывает параллельно — `handle_as_tasks=True` по умолчанию) занимали один и тот же слот.
- На шагах с документами и суммой видна **только «❌ Отмена»**.
- `handlers/fallback.py` подключается последним роутером и ловит всё, что не подошло. Молчание в ответ на фото паспорта — худший исход: человек уверен, что документ отправлен.
- Недостачу бот отслеживает сам (`_uploaded_docs`, телефон → принятые `doc_type`) и на `pending` с неполным комплектом просит недостающую страницу вместо «ждите». Кнопка «📄 Отправить документы заново» живёт инлайном на сообщении «проверка ещё идёт», и только там: из меню она уехала 09.08.2026, потому что попадалась на глаза постоянно и читалась как второй штатный шаг.
- `AlfabitClient` наружу бросает **только** `AlfabitError`, включая обрывы, таймауты и не-JSON ответы (коды `NETWORK`/`BAD_RESPONSE`). Раньше транспортное исключение пролетало мимо `except AlfabitError`, а глобального error-хендлера у бота нет — сценарий умирал молча. Alfabit стоит за Cloudflare и уже отдавал 522 с HTML вместо JSON.
- Скачивание файла из Telegram обёрнуто: `getFile` не отдаёт больше 20 МБ, хотя Alfabit принимает до 25 МБ.

**Документы копятся в буфере и уходят комплектом (решено 09.08.2026).** Раньше каждое фото отправлялось в Alfabit сразу, и состояние «половина комплекта» существовало у них всё то время, пока человек ищет вторую страницу — а если он не вернулся, то навсегда. Выбраться из этого нельзя: ветка `pending` в `_route_by_kyc` только просит ждать, шага загрузки в ней нет, поэтому повторный вход в оплату упирается в тот же `pending`.

Теперь `handle_document` кладёт в данные FSM **`file_id`, а не байты** (файл и так хранится у Telegram, нам нужна ссылка; на диск бот по-прежнему не пишет), а `_send_documents` отправляет комплект целиком. Эндпоинт у Alfabit поштучный, батча нет — комплект всё равно уходит двумя запросами, так что окно «половина комплекта» не исчезает, а сжимается с человеческого масштаба до промежутка между двумя вызовами. Разница в том, что теперь есть кому это заметить: ссылки на файлы на руках, упавший документ переспрашивается точечно, а уже принятые повторно не шлются (`uploaded` в данных FSM). Побочно: размер проверяется по `file_size` **до** скачивания, а не по факту падения `getFile` на 20 МБ.

**Альбомы отклоняются (решено 09.08.2026).** Замок задаёт очередь, но не порядок: задачи приходят к нему в порядке планировщика, а не по `message_id`. Для двух снимков одним сообщением это значит, что пара может переставиться и прописка уедет как `passport_main` — оба файла на месте, бот доволен, а разбирается человек на стороне Alfabit; отказ по KYC приходит молча и через ручную сверку. Поэтому при `media_group_id` бот просит прислать по одному и говорит, какую страницу ждёт сейчас. Ответ идёт **один на альбом** (последний отклонённый `media_group_id` на пользователя лежит в памяти) — иначе на два снимка прилетают два одинаковых упрёка подряд. Потери удобства нет: страницы и так спрашиваются по очереди, отдельным вопросом на каждую.

**Недостачу помним сами (решено 09.08.2026).** Alfabit не отвечает на вопрос «чего не хватает»: проверено на живом API — у `approved`-плательщика с обоими документами `GET /payers/{phone}` отдаёт тот же `required_documents`, что и у номера, который сервис видит впервые. Полей о загруженных документах в ответе нет вовсе. Поэтому `_uploaded_docs` (телефон → принятые `doc_type`) ведётся на нашей стороне, и ветка `pending` в `_route_by_kyc` при неполном комплекте отправляет за недостающей страницей, а не в «ждите». Это закрывает и остаток от буфера: если вторая загрузка упала, а человек нажал «Отмену» (данные FSM стираются), возврат по тому же номеру всё равно ведёт к дозагрузке.

Память живёт в процессе. На диск не пишем сознательно — это снова был бы телефон в файле, от чего отказались 08.08. После перезапуска бота недостача неизвестна, и остаётся ручной путь — инлайн-кнопка «📄 Отправить документы заново» на сообщении «проверка ещё идёт». В меню её нет: там она попадалась на глаза постоянно и читалась как второй штатный шаг, хотя нужна в редком случае.

**Кнопка повтора вернулась на сообщение статуса (решено 10.08.2026).** 09.08 её убрали и оттуда — и выяснилось, что тогда у зависшего `pending` не остаётся выхода вообще. Живой случай: `GET /payers/{phone}` отдаёт `kyc_status: pending`, `processing: false`, `expected_payer_name` заполнено (значит главную страницу Alfabit прочитал), и так больше суток. Все пути ведут в одно «ждите»: ветка `pending` в `_route_by_kyc` после перезапуска процесса видит пустой `_uploaded_docs`, `_missing_docs` возвращает `[]` — и повторный вход по тому же номеру снова упирается в `pending`. Поэтому во второй ветке `kyc_status` (`pending` + недостачи не видно) под сообщением теперь висит `_redo_keyboard()`; в ветке `processing` — по-прежнему нет, там документы прямо сейчас читают. Повторная загрузка того же `doc_type` идемпотентна, так что кнопка безопасна и когда сверка действительно идёт. С 16.08.2026 эта ветка стоит **после** проверки `manual_review`: при ручной сверке кнопки нет, там дока запрещает переотправку.

Чем это **не** лечится: узнать у Alfabit, какие документы у них лежат, по-прежнему нельзя — `GET /payers/{phone}/documents` отдаёт `405`, листинга платежей нет (`GET /checkout/payments` — тоже `405`). ~~То есть «идёт ручная сверка» и «дошла половина комплекта» со стороны бота неразличимы~~ — **это утверждение было неверным**: ручную сверку Alfabit называет прямо, полем `manual_review` в `GET /payers/{phone}`, просто бот его не читал. Исправлено 16.08.2026, см. ниже.

**Прод отставал от репозитория на пять коммитов (10.08.2026).** Тот же разбор: на VPS работал образ, собранный 08.08 из `a8b5da8`, то есть **без** всего, что описано выше — `handlers/fallback.py` в той сборке нет вовсе, `kyc_status` безусловно делает `set_state(None)`, документы уходят поштучно без замка. Сценарии сбора документов проверены на заглушках (Telegram и Alfabit подменены, FSM настоящий): последовательная пара, альбом, падение на первом и на втором документе с последующим повтором, файл >20 МБ, текст вместо фото.

**Результат верификации приходит человеку сам; «pending» разложен на три случая (решено 16.08.2026).** Разбор жалоб «верификация идёт бесконечно» на двух живых номерах показал две разные поломки, обе — на нашей стороне:

- `+7912…7707`: `kyc_status: approved`, `verified_at` 14.08 22:28 МСК, `manual_review: false`. Человек одобрен и **двое суток об этом не знал**. Бот опрашивал статус 20 секунд после загрузки (`_poll_kyc`) и замолкал навсегда: дальше результат узнавался, только если пользователь сам нажмёт «🔎 Статус верификации».
- `+7978…4832`: `kyc_status: pending`, `processing: false`, `manual_review: true`, `expected_payer_name: null` — ФИО с главной страницы не распозналось, заявку забрал оператор. Бот показывал ему «проверка ещё идёт» и кнопку «отправить документы заново», то есть советовал ровно то, что дока запрещает в этом состоянии («те же файлы заново не отправляйте»).

Что сделано:

- **`services/kyc_watch.py`** — заявка встаёт под наблюдение при парковке (`_park_until_kyc`) и досматривается опросом раз в минуту до `approved`/`rejected`. Вебхука на смену KYC у Alfabit нет (дока говорит это прямым текстом), опрос — единственный путь. Короткая пачка сразу после загрузки осталась: распознавание обычно успевает, пока человек смотрит в чат.
- **`notify_kyc_resolved` в `handlers/payment.py`** — фоновое уведомление. Входящего апдейта у него нет, поэтому `FSMContext` собирается вручную по `StorageKey`. Если пользователь в этот момент в другом сценарии, состояние **не трогаем**: перебить чужой шаг — тот самый класс ошибок, из-за которого 08.08 терялись документы. Тогда просто сообщаем результат.
- **Три ветки вместо одной.** `processing: true` — «идёт распознавание»; `manual_review: true` — «проверяет сотрудник», без кнопки повтора и без вопросов про недостающий документ (при ручной сверке `_missing_docs` игнорируется — ждёт оператор, а не человек); остальное — прежняя ветка с `_redo_keyboard()` для случая «половина комплекта после перезапуска».
- **`low_confidence` больше не выбрасывается.** Поле приходит в ответе на загрузку документа и **только там** — в `GET /payers` его нет. Раньше из всего ответа в лог шло одно `processing`. Теперь страница, про которую сервис сказал «читается плохо», называется человеку сразу, пока он ещё в чате и паспорт под рукой. Второй косвенный признак — пустой `expected_payer_name` после распознавания.
- **`services/kyc_trace.py`** — след KYC в логах: `user_id`, маскированный телефон (`+7***7707`), `kyc_status/processing/manual_review`, признак наличия ФИО, `low_confidence` на загрузке, связка `external_payment_id ↔ payment_uid ↔ user_id`. Полный телефон в лог не пишем: логи лежат на диске, а от хранения номеров отказались 08.08.
- **`handlers/errors.py`** — глобальный error-хендлер на Dispatcher. Раньше исключение вне `except AlfabitError` уходило в лог aiogram, а пользователь не получал ничего; молчание в этом боте — худший исход.
- Телефон в URL теперь без «+» (`AlfabitClient._path_phone`), как требует дока. Проверено 16.08.2026: сервер принимает обе формы и отдаёт одну и ту же запись, так что причиной зависаний это не было.

Реестр наблюдения живёт в памяти процесса — после перезапуска слежение теряется, и человек снова остаётся с кнопкой в меню. Это тот же размен, что и с `_uploaded_docs`: писать телефоны на диск было бы возвратом к удалённому `services/user_phones.py`. **Открыто:** если случай «бот перезапустился, пока заявка на сверке» окажется частым, решение придётся пересмотреть — других вариантов, кроме персистентности, тут нет.

Проверено на заглушках (Telegram и Alfabit подменены, FSM настоящий): наблюдение доводит `pending → approved` до одного уведомления и снимает заявку; сбой API заявку не теряет; фоновое одобрение при свободном пользователе переводит на шаг суммы, при занятом — не трогает чужое состояние; ветки `manual_review` / `processing` / «половина комплекта» дают разные тексты и разные клавиатуры; `low_confidence` доходит до человека с названием конкретной страницы; падение на второй странице переспрашивает только её.

**Ожидание KYC — через меню, а не инлайн-кнопку.** Пока документы на проверке, в главном меню появляется четвёртая кнопка «🔎 Статус верификации» (`kyc_menu_keyboard` в `handlers/start.py`), а FSM очищается — пользователь свободно ходит по боту и проверяет статус когда захочет. Сообщение о статусе всегда одно: следующая проверка удаляет предыдущее и шлёт новое вниз чата (`_status_messages` в `handlers/payment.py`, в памяти). Кнопка уходит сама, как только любой возврат в меню отправит обычный `main_keyboard`.

**Удаляемое сообщение не должно ставить меню.** Сообщение о статусе живёт в одном экземпляре: следующая проверка удаляет предыдущее (`_status_messages`). Вместе с удалённым сообщением у пользователя пропадает и reply-клавиатура, которую оно поставило, — так после переноса кнопки повтора в инлайн человек остался вообще без меню. Разделено на два помощника: `_replace_status` шлёт удаляемое сообщение и принимает **только инлайн**-разметку, `_menu_message` ставит меню и как статусное не регистрируется. Клавиатуру с кнопкой «🔎 Статус верификации» ставит `_pending_kyc_notice` — оно из неудаляемых.

**Телефон плательщика нигде не сохраняется (решено 08.08.2026).** Номер спрашивается заново при каждой оплате — кнопкой «📱 Отправить мой номер» либо вводом руками. Прежний `services/user_phones.py` (JSON `user_id → +7…`, `PHONE_STORE_PATH`, volume `./data`) удалён вместе с переменной и volume'ом; на диск бот теперь не пишет ничего.

Кнопке «🔎 Статус верификации» телефон всё же нужен — она берёт его из данных FSM. Пока документы на проверке, вместо `state.clear()` вызывается `_park_until_kyc()`: состояние сбрасывается в `None` (пользователь свободно ходит по боту), а данные с телефоном остаются. Хранилище FSM — `MemoryStorage`, поэтому связка живёт до перезапуска процесса; после рестарта кнопка отвечает «начните оплату заново». Это осознанный размен: раньше ровно ради этого случая и держался файл на диске.

Полностью убрать поле ввода на шаге с телефоном Bot API не позволяет — reply-клавиатура всегда рисуется над ним. Ограничиваемся `input_field_placeholder`; ввод руками остаётся рабочим и валидируется.

**Закрытые вопросы (06.08.2026, проверено на боевых ключах `pk_live_`/`sk_live_`):**
- `payer_ip` — поддержка alfabit ответила: слать **IP сервера, на котором работает бот**. Реализовано: `ALFABIT_PAYER_IP` из `.env`, иначе автоопределение при старте (`services/public_ip.py` → api.ipify.org / ifconfig.me / icanhazip.com). Без IP checkout не включается, строка курса работает как раньше.
- Query в подписи GET — сервер принимает обе формы (с query и без). Оставлен вариант с query.
- Подпись multipart — с пустым body; проверено: настоящий multipart-запрос доходит до валидации (422 `field required: file`), а не отбивается по подписи. Антифрод-поля (`payer_ip`) идут отдельными полями формы. **Осторожно при отладке:** `aiohttp.FormData` без файлового поля сериализуется в `x-www-form-urlencoded`, а не в multipart, и такой запрос отбивается с `401 INVALID_SIGNATURE`. Проба «POST без файла» поэтому вводит в заблуждение — она проверяет не тот content-type. В `upload_payer_document` файл добавляется всегда, так что боевой путь корректен.
- Документы: `doc_type` ∈ `passport_main | passport_registration | selfie`, JPEG/PNG/PDF до 25 МБ. Профиль по умолчанию требует `passport_main` + `passport_registration`. Ответ приходит с `processing=true`, финальный статус — опросом `GET /payers/{phone}` (`processing:false` + `kyc_status`). Повторная загрузка того же `doc_type` идемпотентна.
- `expected_payer_name` из `GET /payers/{phone}` — обязательно показывать плательщику: банк сверяет реального отправителя с паспортом.
- Доступный канал приёма (`GET /checkout/channels`): `RUB_sbp_232` — «Приём мерчанта: QR+KYC white-label виджет».

**Наценка QR+KYC:** цена юаня = `курс витрины alfabit / 6.63 × 1.007` (+0.7%: клиент понижал до 0.6% 08.08.2026 и вернул 0.7% 17.08.2026). Задаётся `ALFABIT_USDT_MARKUP`; дефолт в `config.py` тоже 1.007, чтобы наценка не пропала, если переменную забудут в `.env` на сервере. Наценка применяется и к строке курса, и к сумме платежа — они считаются из одного кешированного значения.

**Курс QR+KYC берётся с витрины кабинета, а не из integration API (решено 08.08.2026).** Подписанный `GET /integration/converter/fiat/rate?direction=buy` отдаёт **базовый** курс конвертера (`rate_effective`, на 08.08 — 84.13). В кабинете на виджете «Купить USDT» покупатель видит другое число — 85.64, потому что поверх базы начисляется **комиссия метода оплаты**. Разрыв 1.8% — больше всей наценки, то есть на базовом курсе юань продавался бы дешевле витрины Alfabit.

Витринный курс собирается двумя **публичными** запросами (ни ключа, ни подписи; префикс именно `/wallet-web/api/v1` — под `/api/v1` отдаётся HTML одностраничника):

```
GET /wallet-web/api/v1/public/fiat-converter/rate?crypto_symbol=USDT&fiat_code=RUB&direction=buy
    → rate_usdt_fiat 82.40, spread_percent 2.10, rate_effective 84.1304, expires_in_seconds 30
GET /wallet-web/api/v1/public/buy-sell/banks/RUB
    → список методов; QR = код SBPRUB, deposit_fee_percent 1.80
курс витрины = rate_effective × (1 + deposit_fee_percent/100)
```

`rate_effective` из публичного эндпоинта совпадает с подписанным до знака — это один и тот же конвертер, просто публичная дверь. Комиссия **не зашита в код**, читается при каждом обновлении: сменят 1.80 на 1.60 — цена поедет за кабинетом сама. Сейчас у всех 22 методов (QR, S-Pay, T-Pay, «Любой банк», …) она одинаковая, 1.80%.

Сверка с кабинетом 08.08.2026: `84.1304 × 1.018 = 85.6447` против `85.645467` на экране при выбранном QR — расхождение 0.0007 ₽. S-Pay на скрине лёг на `84.1304 / (1 − 0.018)`; разница между «×(1+f)» и «/(1−f)» — 0.03%, в копейках цены юаня не видна. Взят вариант `×(1+f)`, совпавший именно с QR.

Запасные пути в `AlfabitWidgetProvider` (эндпоинты недокументированы — это внутренний API сайта, могут смениться): если лёг публичный курс — берётся подписанный; если лёг список банков — последняя известная комиссия из памяти провайдера. Если комиссии не видели ни разу (холодный старт при недоступном эндпоинте) — провайдер **падает намеренно**, а не отдаёт курс без комиссии: `RateCache` сохранит предыдущее значение, на холодном старте строка QR+KYC просто не покажется. Тихо занизить цену на 1.8% хуже, чем не показать её вовсе.

**Открыто:** 1.80% — комиссия розничного пополнения. У мерчантского канала приёма `RUB_sbp_232` (наш QR+KYC) в `GET /checkout/channels` стоит `fee_percent: null`, то есть своя тарификация, величина неизвестна. От неё зависит, сколько из +0.7% реально остаётся. Вопрос к поддержке Alfabit, кодом не выясняется.

Право `can_converter_execute` (открывает `POST /converter/fiat/estimate` — исполняемая котировка на конкретную сумму — и `POST /converter/fiat/execute`) для витринного курса **не нужно**. Если будете его запрашивать, учтите: судя по всему, это одно право на расчёт и на исполнение, то есть ключ в `.env` получит возможность двигать деньги между балансами. Вызовов `execute` в коде бота нет.

**Блокер прав ключа снят (08.08.2026).** Раньше все POST-эндпоинты checkout отвечали `403 PERMISSION_DENIED` (`required_permission: can_invoices_create`), из-за чего флоу останавливался на загрузке документов. После выдачи права проверено на боевых ключах прямо в контейнере:
- `POST /checkout/payments` с телом `{}` → `422 Field required` (amount, external_payment_id) — подпись принята, право есть;
- `POST /checkout/payers/{phone}/documents` настоящим multipart без файла → `422 Field required: file` — то же самое;
- чтение работает как и работало (`GET /converter/fiat/rate`, `/checkout/channels`, `/checkout/payers/{phone}` → 200).

То есть 403 больше нигде не возникает и платёжный флоу проходим целиком.

**Закрыто (08.08.2026): `direction=buy`.** Конвертер котирует симметрично вокруг стакана Alfabit: при книге bid 83.00 / ask 83.45 он отдавал `sell` 82.40 и `buy` 84.13. Направление читается с позиции клиента: `sell` — вы продаёте USDT, `buy` — покупаете. Рубли от плательщика мы конвертируем в USDT, то есть покупаем его, значит наша сторона — `buy`. На `sell` курс был занижен примерно на 2% — больше самой наценки +0.7%. Дефолт в `config.py` переведён на `buy`; переменной `ALFABIT_RATE_DIRECTION` в `.env` нет, работает дефолт.

**Строка «Курс юаня: 6.63»** (делитель понижен с 6.67 клиентом 11.08.2026) в сообщении курса — просто справочная величина (юаней за доллар), без привязки к бирже. Выводится из `services.yuan.DIVISOR`, то есть из той же константы, по которой считается цена, — чтобы показанное число не разошлось с реальным делителем.

**Стакан Alfabit как альтернатива конвертеру — рассмотрен и отклонён (08.08.2026).** У Alfabit три модуля: Crypto Spot, Fiat Spot (реальный стакан USDT/RUB на движке Stockbook) и Converter. Публичные эндпоинты Fiat Spot работают **вообще без ключа и подписи**: `GET /api/v1/integration/spot/fiat/{orderbook,stats,instruments}` (+ публичный WS: orderbook, trades, stats, charts). Технически это полный аналог Rapira. Не используем по двум причинам: (1) книга тонкая — оборот за сутки ~12 400 USDT при 212 сделках, причём `high = low = open = last`, инструмент с `require_market_maker: true`, такую цену двигает один ордер; (2) котировка конвертера — обязательство, по которому Alfabit исполнит обмен, а цена в стакане никому ничего не обещает. Сумма QR+KYC — фиксированное рублёвое обязательство перед клиентом, поэтому привязка к твёрдой котировке корректнее.

**Отдельно — крипто-инвойсы** (`/api/v2/integration/invoices`): приём криптовалюты без KYC, проще checkout. Пока не используем, зафиксировано как альтернатива.

## Отклонённые подходы (не реализовывать, если не попросят явно)

- **Скрапинг investing.com напрямую** — сайт активно защищается от ботов (Cloudflare), нет официального API, риск нарушения ToS.
- **CyberScraper 2077 / AI-скраперы для investing.com** — отклонено. Причины: (1) капча в инструменте решается вручную через GUI-браузер — несовместимо с headless-сервером без монитора; (2) LLM-вызов на каждое извлечение одного числа — абсурдно дорого и медленно относительно задачи; (3) Cloudflare-bypass — гонка вооружений, нестабильно в долгосрочной перспективе; (4) лишняя нагрузка на ресурсы VPS (полноценный браузерный движок Playwright).
- **MOEX как источник USD/RUB** — отклонено. Биржевые торги USD/EUR на Московской бирже приостановлены с июня 2024 (санкции против самой биржи и НКЦ), официальный курс ЦБ сейчас формируется не по биржевым данным.
- **Excel вместо Google Таблиц** — отклонено, остаёмся на Google Sheets.
- **Django + PostgreSQL + Redis + Celery** — отклонено для текущего масштаба. Полная админка на Django была первоначальным планом, но избыточна при ~10 чел/час. Зафиксировать как вариант для будущего роста (см. ниже).
